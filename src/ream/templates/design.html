Backups that look after themselves

Two small things that watch the result rather than the job, and a third that proves a restore still works without anyone remembering to try.

Settled3 modulesWritten

What this is for
"I want to stop having to check whether the backups ran. If they break I want to know, and I don't want to find out six months later when I need one."

Settled since: knowing within a day is soon enough; restore-testing is in scope; failures surface on the board rather than chasing {{owner_them}}; restores are tested monthly on one directory at random.

How it runs

  1. Each morning the freshness check asks the store. Stale or could-not-tell writes a row on the board; fresh writes nothing at all.
  2. On the first of the month the restore prover runs. Failed or could-not-run writes a row; proved writes nothing.
  3. There is no queue, no retry and no state between runs. Each run answers from the store as it is now, so a missed run costs one day of lateness and nothing else — no backlog to drain and no state to corrupt.

When it goes wrong

What failsWhat happens
The store is unreachableReported as could-not-tell, never as fresh. An unknown is a finding; treating it as fine is the failure this whole thing exists to prevent.
The check itself crashesNothing is written, which is invisible — so the check's own last-run time is on the board beside its answer. A checker that can die silently is not a checker.
A restore test half-finishesCould-not-run, not failed. Distinguishing "we could not tell" from "it is broken" is the point; collapsing them costs either trust or attention.
The board is unwritableNothing catches this yet. Named here rather than hidden — see the risk below.

How it is tested

  • Both modules at their own interface, against a fake store: every answer each can give, including the nonsense ones.
  • One end-to-end run a month against the real store, which is the restore test itself — the feature is its own integration test.
  • Not covered: the board being unwritable, and the check being dead for long enough to matter. Both are real and both are listed below rather than quietly left out.

What could still bite

The checker can die and take its own alerting with it

If the thing that reports failures is itself down, everything looks fine. Its last-run time goes on the board so the silence is visible, but nothing actively notices — and a human spotting a stale timestamp is exactly the failure mode being designed out. Accepted for now, tracked, and the cheapest fix is a second check watching the first from somewhere else.

A monthly restore of one random directory can miss rot for months

Rot in a directory that is never picked is not caught. Accepted deliberately: testing everything costs a full download each time, which was the trade-off settled on the intent page. Revisit if a test ever finds something — one real finding changes the odds enough to reprice it.
