Backups that look after themselves

Working out what this should actually be before building any of it. Three questions below are open and your answers change the shape.

3 questions open2 settledUpdated

What you asked for

"I want to stop having to check whether the backups ran. If they break I want to know, and I don't want to find out six months later when I need one."
  • Q1 (a): knowing within a day is soon enough — this does not need to be instant.
  • Q2 (b): a restore that is never tested does not count as a backup, so testing restores is in scope, not a later nicety.

What this is and is not

In scope
  • Knowing, without looking, that last night's backup happened.
  • Proving a restore works, on a schedule, without anyone remembering.

Not in scope

  • Backing up anything not already backed up. This is about trust in what exists, not coverage.
  • Off-site for the media library. Separately argued; it is 8 TB and it changes the economics of everything here.

The one real fork

Where the checking lives

On the backup host itself

Simple, no new moving parts. But a host that is down cannot report that it is down, which is the failure most worth catching.

Somewhere else, asking the off-site store

Survives the host being dead, because it never talks to it — it asks the store how old the newest copy is. One more thing to run.

I would take the second. The whole point is catching the case where something is wrong, and "the host is off" is the most likely something. A checker that dies with the thing it checks is decoration.

Open questions

Q3How loud should a failure be?

Changes what gets built: a page you check is an afternoon, a message that finds you is a week and needs somewhere to send it.

  1. It turns up on this board, and you see it when you look. — my recommendation, given Q1
  2. A message that reaches you wherever you are.
  3. Something else — say what.
Q4How often should a restore be tested?

Each test costs a full download, so this is the difference between a few pounds a year and a few pounds a month.

  1. Monthly, one directory chosen at random. — my recommendation: catches rot without the full cost
  2. Quarterly, everything.
  3. Something else — say what.
Q5If a restore test fails, should it retry before telling you?

A retry hides a flaky network, which is good. It also hides a real fault for another month, which is not.

  1. Tell you immediately, every time. — my recommendation: a false alarm costs a minute, a hidden fault costs the backup
  2. Retry once the next night, then tell you.
  3. Something else — say what.
